# 2.10 — Extensions

Теория **с нуля**. Практика обязательна до контроля.

---

## 1. Зачем extensions

Иногда хочется добавить метод к **уже существующему** типу (`String`, `int`, свой класс), не меняя исходный код типа и не делая subclass.

```dart
extension StringX on String {
  String shout() => '${toUpperCase()}!';
}

void main() {
  print('hi'.shout()); // HI!
}
```

`extension Имя on Тип` — «добавь члены, которые выглядят как методы/геттеры этого типа».

---

## 2. Что это не меняет

Extension **не** добавляет настоящее поле внутрь объекта и **не** ломает инкапсуляцию чужого класса магически. Это синтаксический сахар: компилятор переписывает вызов в обычную функцию.

Учебно: ` 'hi'.shout() ` ≈ ` StringX('hi').shout() ` (упрощённо).

Нельзя из extension лезть к приватным членам другого library так, как будто ты внутри класса.

---

## 3. Геттеры в extension

```dart
extension IntX on int {
  bool get isEvenNumber => this % 2 == 0;
}

print(4.isEvenNumber); // true
```

`this` — значение слева от точки.

---

## 4. Когда использовать

- Удобные хелперы для `String` / `DateTime` / своих типов.
- Не вместо нормального класса, если нужна своя сущность с состоянием.

---

## 5. Сравнение с JS

Похоже на идею «добавить метод в прототип», но в Dart безопаснее по модульности: extension видно там, где его импортировали. Не загрязняет глобально всё подряд без import.

---

## 6. Типичные ошибки

1. Думать, что extension хранит новые поля в объекте.
2. Прятать бизнес-логику огромного размера в extensions вместо сервиса/класса.
3. Конфликт двух extension с одинаковыми именами методов — нужна явная квалификация.

---

## 7. Чеклист

- синтаксис `extension Name on Type`;
- метод и геттер;
- это сахар, не subclass;
- зачем import.
