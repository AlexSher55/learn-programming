# 1.2 — Stack, Heap, Call Stack, GC

Статус: тема закрыта на 100%. Это конспект для повторения.

---

## 1. Зачем две «зоны» памяти

В учебной модели рабочую память программы удобно делить на:

- **Stack** — для короткой, структурированной работы вызовов функций;
- **Heap** — для объектов, которые живут дольше и создаются динамически.

Это не «два разных компьютера», а **модель**, как runtime раскладывает данные.

---

## 2. Stack — стопка тарелок (LIFO)

**LIFO** = Last In, First Out: последним положили — первым сняли.

Аналогия: стопка тарелок.
- положил сверху;
- снять можно только верхнюю.

В программах на stack кладут **stack frame** (кадр вызова) для каждой активной функции.

В кадре обычно (упрощённо):
- параметры функции;
- локальные переменные;
- служебная информация «куда вернуться после return».

---

## 3. Call stack — стопка активных вызовов

**Call stack** — stack, где лежат кадры сейчас выполняющихся функций.

Пример:

```text
main() вызывает a()
a() вызывает b()
b() выполняется
```

Стопка примерно такая (сверху — текущий кадр):

```text
[ b ]
[ a ]
[ main ]
```

Когда `b` закончилась → кадр `b` снимается → управление возвращается в `a`, и т.д.

Связь с функциями Dart (тема 2.3): каждый вызов функции = новый кадр на call stack.

---

## 4. Stack overflow

Если функции вызывают друг друга слишком глубоко (часто бесконечная рекурсия), кадры накапливаются, пока память стека не закончится → **stack overflow**.

Учебный образ:

```text
f() вызывает f() вызывает f() ... без конца
```

Стопка растёт, пока не «переполнится».

---

## 5. Heap — склад объектов

**Heap** — область, где живут динамические объекты: списки, объекты пользователей, многие структуры данных.

Почему не всё на stack:
- объект может быть нужен дольше, чем один вызов функции;
- размер может быть заранее неизвестен;
- на один объект могут ссылаться из разных мест.

Переменная часто хранит не «весь объект в себе», а **ссылку** на объект в heap.

Подробнее: урок 1.3.

---

## 6. Достижимость и GC

**GC (Garbage Collector)** — механизм, который убирает объекты, которые программе уже не нужны.

Как GC понимает «не нужен» в учебной модели? Через **достижимость**.

Объект достижим, если до него можно добраться по цепочке ссылок от «корней» (локальные переменные активных кадров, глобальные и т.п.).

- Есть хотя бы одна цепочка ссылок → объект жив.
- Цепочек не осталось → объект **недостижим** → GC **может** его удалить.

Важно:
- GC не обязан удалить мгновенно в ту же миллисекунду;
- но модель такая: недостижимое — кандидат на очистку.

---

## 7. `return` не «оставляет объект магически»

Отдельно (из закрытой темы, часто на JS-примерах):

- `return value;` — отдаёт значение наружу;
- `return;` или отсутствие return в JS-функции → наружу уходит `undefined`;
- объект сам по себе «не возвращается», если ты его не вернул через `return` / не сохранил ссылку снаружи.

Если ссылок на объект больше нигде нет — он становится недостижимым.

---

## 8. Картина целиком

```text
Call stack (кадры функций)
  └── локальная переменная user ──ссылка──► объект User в Heap

Heap
  └── объекты, до которых есть ссылки — живы
  └── объекты без ссылок — может убрать GC
```
