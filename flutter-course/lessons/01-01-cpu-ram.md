# 1.1 — Как работает программа: CPU и RAM

Статус: тема закрыта на 100%. Это конспект для повторения.

Ты frontend-разработчик, но под капотом любой язык (JS, Dart, Flutter) всё равно бежит на железе. Без этой картины потом плохо понимаются ссылки, stack overflow, память и производительность.

---

## 1. Зачем это Flutter-разработчику

Flutter-приложение — тоже программа:
- код выполняется процессором (CPU);
- данные живут в оперативной памяти (RAM);
- переменные, списки, виджеты — всё это модели поверх RAM.

Если понимать CPU/RAM, легче понимать:
- почему «тяжёлый» цикл тормозит UI;
- что такое ссылка на объект;
- куда «деваются» объекты и зачем GC.

---

## 2. CPU — исполнитель инструкций

CPU не «понимает Flutter». Он снова и снова делает цикл:

1. **Fetch** — взять следующую инструкцию из памяти;
2. **Decode** — понять, что это за команда;
3. **Execute** — выполнить.

Потом снова Fetch → Decode → Execute.

Грубо: CPU — очень быстрый рабочий, который читает рецепт построчно и делает ровно то, что написано.

Программа на Dart сначала переводится в вид, который машина умеет выполнять. Для учебной модели достаточно: «твой код в итоге становится последовательностью инструкций для CPU».

---

## 3. RAM — рабочий стол программы

**RAM** — быстрая рабочая память, пока программа запущена.

Аналогия:
- диск/SSD — шкаф (долго хранить);
- RAM — стол (сейчас работаем);
- CPU — руки, которые берут вещи со стола и делают работу.

Когда программа запущена, в RAM лежат:
- код (упрощённо);
- переменные;
- объекты;
- служебные структуры (stack и т.д.).

Когда программа закрылась — этот рабочий стол обычно очищается (упрощённо).

---

## 4. Переменная — не «сама коробка с объектом навсегда»

Имя вроде `age` или `user` — это **слот** (ячейка/наклейка), в котором лежит:
- либо простое значение;
- либо **ссылка** (адрес/указание) на объект в другом месте памяти.

Подробнее про ссылки — в уроке 1.3. Здесь главное:

> Имя переменной и объект в памяти — не всегда одно и то же.

Один объект может быть доступен через **несколько имён** (несколько ссылок на него).

---

## 5. Массив/список: индекс ≠ адрес в RAM

В коде мы пишем `items[0]`, `items[1]`, `items[2]`.

Это **индексы** — удобные номера с нуля для программиста.

Внутри RAM у элементов есть **адреса** (где физически/логически лежит байт).

Индекс `0` — не значит «адрес 0 в компьютере».

### Упрощённая формула

Если элементы лежат подряд и каждый занимает одинаковый размер:

```text
адрес_элемента = baseAddress + index * elementSize
```

Где:
- `baseAddress` — адрес начала массива (элемента с индексом 0);
- `index` — номер элемента;
- `elementSize` — размер одного элемента в байтах (учебная модель).

Пример:
- начало массива по адресу `1000`;
- каждый элемент по `4` байта;
- элемент с индексом `3` → `1000 + 3 * 4 = 1012`.

Зачем это знать:
- понятно, почему доступ по индексу в массиве обычно быстрый;
- индекс — логика языка, адрес — модель памяти.

---

## 6. Сравнение с тем, что ты знаешь из JS

В браузере ты тоже не руками кладёшь байты в RAM, но модель та же:
- JS-значения живут в памяти движка;
- объекты доступны по ссылкам;
- CPU выполняет код JS (через движок).

Dart/Flutter — другой язык и runtime, но железо то же по сути: CPU исполняет, RAM хранит рабочее состояние.
